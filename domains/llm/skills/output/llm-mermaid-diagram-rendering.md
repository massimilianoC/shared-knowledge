# Skill: LLM-Generated Mermaid Diagram Rendering

## Description
Implements or debugs client-side rendering of Mermaid diagrams generated by an LLM inside a
chat/markdown UI (React, Vue, Svelte, or vanilla JS). Handles predictable LLM syntax mistakes,
safe injection into a framework-owned DOM, and correct behavior when the diagram source arrives
incrementally via streaming. Suitable for any frontend that renders LLM output containing
Mermaid fenced code blocks.

## Expected inputs
- `rawDiagramSource: string` — the Mermaid source as emitted by the LLM, possibly incomplete if
  streaming.
- The UI framework in use (React/Vue/Svelte/vanilla) — determines the raw-HTML injection
  primitive and state-reset mechanism.
- Whether the content can change after first mount (streaming) or is static once received.

## Produced outputs
- A rendered SVG diagram, or a source/error fallback view if both raw and normalized parsing
  fail.
- No permanent "stuck" state across streaming updates — the fallback view only appears for
  content that is genuinely invalid once fully arrived.

## Steps / Procedure
```
rawDiagramSource (possibly incomplete, mid-stream)
    │
    ▼
[1] Validate            → mermaid.parse(code, { suppressErrors: true })
    │  (fails)
    ▼
[2] Normalize + re-validate → regex fixups for known LLM mistakes, parse() again
    │  (still fails)
    ▼
[2b] Fall back to source view — only after BOTH raw and normalized fail
    │  (succeeds, at either stage)
    ▼
[3] Render into a detached scratch node → extract serialized SVG string
    │
    ▼
[4] Reset all transient state at the START of this attempt (not just on success)
    │
    ▼
Inject SVG string via the framework's raw-HTML primitive
```

## Critical rules

### Stage 1 — Validate
- Always call `mermaid.parse(code, { suppressErrors: true })` before ever calling
  `mermaid.render()` — never render unvalidated code.
- Initialize once at module scope: `mermaid.initialize({ startOnLoad: false, securityLevel:
  'strict', flowchart: { htmlLabels: false } })`. `securityLevel: 'strict'` sanitizes output SVG
  via DOMPurify and matters specifically because the content is LLM/untrusted-sourced — don't
  relax it without a specific reason.

### Stage 2 — Normalize, then re-validate
- Apply cheap regex fixups for recurring LLM mistakes: trailing semicolons; unquoted
  square-bracket/curly-brace labels containing `()`/`:`/`/`/`?`; unquoted multi-word `subgraph`
  titles.
- Re-run `parse()` on the normalized version. Only fall back to a source view if **both** the raw
  and normalized versions fail.
- Extend the fixup list as new patterns are found, but always pair a new regex with re-validation.

### Stage 3 — Render into a scratch node
- Never point `mermaid.render()` at a DOM node the framework owns — create a detached
  `document.createElement('div')`, append off-screen to `document.body`, render into it, extract
  the SVG string, remove the scratch node in a `finally` block. See
  [render-into-scratch-node-not-framework-dom](../../knowledge/decisions/render-into-scratch-node-not-framework-dom.md).
- Use a random suffix on the render id (`crypto.randomUUID()`) so rapid re-renders never collide.
- **The one rule that matters most:** never let a container element receive both real framework
  children and the raw-HTML-injection prop at the same time — even a conditional child like
  `{!svg && <span>Loading…</span>}` counts as "has children" to React regardless of its runtime
  value, and React throws a hard render-crashing error the moment the injection prop is also
  present. Put each mode (loading vs. rendered) in its own, mutually exclusive element.

### Stage 4 — Reset state per attempt
- If diagram source can change after mount (streaming), reset error/fallback/previous-output
  state **unconditionally at the top of every attempt**, keyed on the source changing — not only
  in the success branch. See
  [reset-fallback-state-per-streaming-attempt](../../knowledge/decisions/reset-fallback-state-per-streaming-attempt.md).
- Wrap the renderer in an error boundary (or framework equivalent) that itself resets when the
  diagram source prop changes, so a crash on one incomplete version doesn't permanently disable
  later valid ones.

## Testing rules
- Never trust `jsdom` (Vitest/Jest) for real Mermaid rendering — `getBBox` is undefined there,
  failing almost every diagram type regardless of code correctness. Unit-test `parse()`-level
  logic and mocked-`mermaid` component behavior in `jsdom`; verify actual rendering in a real
  browser engine (e.g. Playwright driving Chromium).
- Build a throwaway, app-independent HTML harness (loads the Mermaid UMD bundle directly, no
  bundler/backend/auth) to isolate "is it Mermaid/config" from "is it my framework integration" —
  serve it with a plain HTTP server and drive it with real-browser automation.

## Component naming / decision conventions
| Concern | Rule |
|---|---|
| Fence language routing | Decide explicitly whether ` ```graph ` (a valid top-level Mermaid keyword some models emit instead of ` ```mermaid `) also routes to the renderer — don't let this happen by accident. |
| Markdown sanitizer | If using `rehype-sanitize` or similar, confirm the schema allows `className` matching `/^language-.../` on `<code>` elements, or the renderer never sees the block. |
| Minified error decoding | Fetch `https://raw.githubusercontent.com/facebook/react/main/scripts/error-codes/codes.json` and look up the exact numeric code — don't guess from `node_modules/react-dom` source order. |
| Stale deploy check | Compare the served JS bundle's content-hash filename before/after a rebuild before re-diagnosing a "still broken after redeploy" report. |

## Common pitfalls to avoid
- ❌ A container with both `children` and `dangerouslySetInnerHTML`/`v-html`/`{@html}` — split into
  mutually exclusive branches.
- ❌ Not resetting the fallback/error flag at the start of every render attempt — permanently
  latches the UI on stale state for streaming content.
- ❌ Rendering directly into a framework-owned DOM node instead of a detached scratch node.
- ❌ Trusting `networkidle0`/`jsdom`/unit tests as proof that real rendering works.
- ❌ Passing native function references (not strings) into `page.evaluate()`-style browser-context
  calls under an esbuild/tsx-based build, if the rendering pipeline also drives headless-browser
  capture — for the same class of pitfall in a different pipeline.

## Component naming conventions (regex fixups)
| Prefix | Contract |
|---|---|
| `normalizeXxx` | Fixes a class of recurring syntax mistakes; never throws, returns the input unchanged if no match |
| `resolveRenderableCode` | Tries raw, then normalized; returns `null` only if both fail `parse()` |

## Covered bugs
| Bug | Models/Trigger | Fix |
|---|---|---|
| Container has both `children` and raw-HTML prop | Any framework, any diagram | Mutually exclusive branches (Stage 3) |
| Fallback flag never reset on new streaming chunk | Streaming chat responses | Unconditional reset per attempt (Stage 4) |
| Unquoted labels with `()`/`:`/`/`/`?` | LLM-generated Mermaid | Regex auto-quote (Stage 2) |
| Unquoted multi-word `subgraph` titles | LLM-generated Mermaid | Regex fixup to `subgraph Id["Title"]` |
| `jsdom` fails on real `mermaid.render()` | Any test suite using real Mermaid under jsdom | Mock in unit tests, verify in a real browser |
| ` ```graph ` fence skips the renderer | Models that alias `graph` for `flowchart` | Explicit routing decision |
